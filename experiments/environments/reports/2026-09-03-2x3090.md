# Native environment validation on two RTX 3090 cards

## Verdict

Both **native environments and two-rank CUDA/NCCL canaries are installed and
working**. SimCT's dependency check is clean. X-Token has five explicitly
excluded upstream CUDA 13/transport requirements; its dependency check is
therefore nonzero. **No end-to-end optimizer update has completed yet.**
This report is setup evidence, not an X-Token/SimCT reproduction or a GPU
throughput comparison. The explicitly approved third trainer attempt has now
failed during teacher offload with a CUDA illegal-memory-access error. Canary
success did not establish real-model training success.

The prior machine's setup was not entirely lost: source pins, harness and
earlier unit-test evidence survived. The native overrides/lockfiles were not
previously published. This directory now packages both complete dependency
resolutions instead of relying on a rented machine's mutable venv.

## Diagnoses and continuation gate

1. Missing `+` on newly added Hydra `automodel_kwargs` keys caused launch 1 to
   stop during config parsing (8.661 s). Fixed; config-only validation passed.
2. Choosing the independent uv project as **cwd** caused launch 2 to fail
   loading the upstream relative prompt `examples/prompts/cot.txt` (15.442 s).
   Fixed by setting **NeMo source cwd** and explicit `uv --project <native-env>`.
   Config/tokenizer/data validation now passes without Ray or a training run.

Neither initial launcher failure demonstrates TPU/GPU OOM, bad distillation
math or unsuitable 3090 hardware. Neither produced an optimizer update.

3. User-approved attempt 3 ran the unchanged published code
   `d04f0147171fd9a152942ef720db36c3cc162807`, after a fresh matching config gate.
   Qwen3 teacher initialization reached both Ray workers. During setup,
   `teacher_policy.offload_after_refit()` called `move_to_cpu()` and
   `move_buffer_to_device()`; rank 1 reported a CUDA illegal address at
   `torch.utils.swap_tensors(v, v.to(device))`. Both ranks' NCCL watchdogs then
   aborted. This is before the training loop, so **zero optimizer updates**.
   CUDA is asynchronous: this stack identifies where the error surfaced,
   not necessarily the kernel that originally caused it. Hardware failure,
   OOM, P2P/NCCL incompatibility and a specific package defect are not proven.
   A generic Ray warning listing OOM as one possible cause is not an OOM proof.

The process exited 1 in 37.013 s without hitting its 1200 s timeout. There were
three 15-second telemetry samples; the largest sampled memory was 284 MiB per
GPU (not a measured peak). After cleanup, both GPUs returned to 1 MiB/0% with
no training/Ray workers left. Attempt 3 logs, command, result, telemetry, marker
and TensorBoard files have been copied off-host. No fourth run or dependency
change was attempted. A further run requires a separately approved diagnostic
plan, ideally synchronous CUDA error localization at teacher FSDP/offload.
